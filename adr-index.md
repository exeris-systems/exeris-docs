# ADR Index — Exeris Ecosystem

**Single numbering namespace** across all Exeris repositories. ADR files live next to the code they describe; this index is the canonical lookup (number → owning repo + link).

## Rules

1. **Tech-side ADRs only.** Business decisions (legal / IP / financial / procurement) are kept in a separate, private decision registry maintained outside this repository. Refactoring-only ADRs do not enter the registry.
2. **Number reservation.** A number is reserved by a PR to this file before the ADR-content PR merges.
3. **Visibility.** Per ADR-020.
   - `public` — content lives in a public open-core repo.
   - `enterprise-private` — content lives only in a private enterprise repo. Number is publicly registered here, content is not.
4. **Scope.**
   - `per-repo` — bounded to one repo.
   - `cross-repo` — affects multiple repos. Owning repo holds the authoritative copy; every other affected repo has a `docs/adr/ADR-NNN.link.md` stub.
   - `platform` — stack-level recommendation. Owning repo: `exeris-docs`.
5. **Routines and reviewers cite by number**, not by path.

> **Reservation note:** ADR-031 is a number reservation against future name collisions; content lands in a follow-up PR. Per Rule 2, the number is held by this index entry, not by the existence of a content file. ADR-031 covers the kernel-gated half of Phase 3B (W3C `traceparent` propagation + OTel span/metric emission) and waits on a **future** kernel tracing milestone — **not** delivered in `exeris-kernel` 0.8.0. As of 0.8.0 (shipped 2026-06-03) the kernel has **no** tracing logic at all: no `TraceContext` `ScopedValue` carrier, no `PrometheusOtlpTelemetrySink`, no span emission in SPI/Core/Community (the `telemetry.tracingEnabled` / `region` config knobs are parsed but dormant). The kernel-side work is the still-open gap in the kernel ROADMAP §"Telemetry: OTLP Metrics Export and Distributed Tracing", targeted ~Sprint 0.12 / v0.12 of the consolidated 1.0 GA roadmap. ADR-031 therefore remains blocked on that milestone, not on 0.8.0; the earlier "0.8.0" pin was a drift in this note (corrected 2026-06-08). ADR-030 was previously listed as reserved; it was promoted to ACCEPTED 2026-05-17 in the same downstream review that closed Phase 4C — see the linked file. ADR-033 was similarly listed as reserved earlier on 2026-05-18 pending the RFC; it was promoted to ACCEPTED the same day after the RFC was accepted — see `exeris-kernel/docs/rfc/RFC-2026-05-18-kernel-diagnostics-spi.md`. ADR-034 covers the symmetric client-side body codec SPI (parallel to `HttpResponseBodyEncoder` from ADR-009/0.5.0) plus the tier-neutral `KernelWebClient` facade in `exeris-kernel-core`. ADR-034 supersedes ADR-026 (the original `CommunityWebClient` placement) because that decision leaked the Community tier into the build-time surface consumed by `exeris-tooling/KernelClientGenerator`; the supersession lands in lockstep across `exeris-kernel` (SPI + facade), `exeris-tooling` (generator FQN update), and `exeris-kernel-enterprise` (link stub). Pre-1.0 has no external SPI consumers, so the supersession is in-scope for v0.8 Sprint 6. ADR-036 (reserved 2026-06-03) closes the fourth codec quadrant left open after ADR-034: server-side request-body **decode** (`HttpRequestBodyDecoder` + registry + `HttpRequestDecodingContext`), mirroring the client-side `HttpResponseBodyDecoder`. Its motivation is not symmetry-for-symmetry but removal of a build-time Wall breach — today `exeris-tooling/KernelHandlerGenerator` emits a hard-wired Jackson `MAPPER` + `JacksonException` catch into every generated controller's `parseBody`, the only codec quadrant with no SPI seam. Lands lockstep across `exeris-kernel` (SPI + `CommunityJsonRequestBodyDecoder` driver + TCK), `exeris-tooling` (generator resolves the registry instead of inlining), and `exeris-kernel-enterprise` (link stub); in-scope for v0.8 Sprint 7. ADR-038 (accepted 2026-06-05) is the **SDK-side realization** of the ecosystem capability-composition model fixed in ADR-024: it records where the `@CapabilityModule`/`@Provides`/`@Requires`/`@CapabilityLifecycle` annotations are defined (`exeris-sdk-annotations`, new `capability` subpackage), that services are referenced by `Class<?>` and persisted in the AST as source-written name strings (tooling-normalized to FQN), and that the lifecycle interface, licensing taxonomy (ADR-023), and `cap-manifest.json` discovery format stay out of the SDK. It is to ADR-024 what ADR-037 is to the `-io` module: a thin "implements" record owned by `exeris-sdk`, driven by [RFC-2026-06-03](../exeris-sdk/docs/rfc/RFC-2026-06-03-capability-annotation-surface.md). ADR-041 (accepted 2026-06-09) is owned by `exeris-spring-runtime` and follows the single-decider accepted-on-merge pattern: it records the decision to re-activate Spring Boot's servlet-web-gated OAuth2 resource-server `JwtDecoder` inside Compatibility Mode when the app runs Exeris-hosted with `spring.main.web-application-type=none`, so a brownfield JWT resource server keeps working after migrating onto the Exeris runtime. It is **narrow by design** — it covers only the resource-server JWT decoder (built with public Spring Security factories, mirroring Spring Boot's own validator wiring) and explicitly defers the broader "which servlet-web-gated auto-configs does Exeris compat re-activate under `none`" policy to a future RFC. Content and the thin decoder implementation land together in the `exeris-spring-runtime` PR that introduces `docs/adr/ADR-041-compat-resource-server-security-under-none.md`. ADR-045 (reserved 2026-06-25) resolves the client-side retry deferral that ADR-026 (§"no implicit retry") and ADR-032 (Alternative D) both named but left open: an opt-in `HttpRetryPolicy` SPI in `eu.exeris.kernel.spi.http` (`HttpRetryPolicy` / `HttpAttemptOutcome` / `RetryDecision`) consumed by `KernelWebClient` through one constructor parameter (default `none()`, preserving the ADR-026 surface), with the **behavioural** policy — idempotency gate, `502/503/504` + transport retry, `Retry-After`/`SHED_LOAD` (ADR-010) handling, capped exponential backoff + jitter — shipped in `CommunityHttpRetryPolicy`, **not** baked into the SPI, so consumer alignment (tooling / migration tool / BudgetHQ) can tune defaults without ADR churn. The retry seam re-encodes the typed body per attempt (no `LoanedBuffer` retained across attempts), so the codec path's zero-leak invariant is untouched. Content drafted on the kernel v0.10 train (Sprint 4 — HTTP Client codec/retry); lands lockstep across `exeris-kernel` (SPI + `KernelWebClient` loop + `CommunityHttpRetryPolicy` + TCK) and `exeris-tooling` / `exeris-kernel-enterprise` (link stubs). ADR-046 (reserved 2026-06-29) carries the body-codec matrix (ADR-009/034/036) onto the **events** surface: a tier-neutral `EventPayloadCodec` + `EventPayloadCodecRegistry` in `eu.exeris.kernel.spi.events.codec`, registry-selected by `(payloadType, contentType)` with a Community JSON driver, resolved **in the generated `*EventPublisher`** (ADR-036 "site B") so `EventBus`/`EventEngine` stay byte-for-byte unchanged and the wiring rides a new optional `KernelProviders.EVENT_PAYLOAD_CODEC_REGISTRY` slot (the `EVENT_STREAM_READER`/`EVENT_STREAM_APPENDER` precedent, **not** `HttpKernelProviders`). It unblocks the EV1 runtime half — today the generated publisher ships `EventPayload.empty()`, so generated domain events carry no data. Strictly additive (SPI types + driver + slot + `AbstractEventPayloadCodecTck`); lands lockstep with the `exeris-tooling` `KernelEventGenerator` rewrite that builds the redacted payload object and resolves the registry. Content is DRAFT in `exeris-kernel`; **targeted v0.10**, sequenced with the Events `topic` item. The kernel SPI + Community driver + TCK land first (the slot ships defined-but-unbound, the `EVENT_STREAM_*` precedent); the bootstrap slot-binding + generator rewrite follow lockstep. ADR-047 (accepted 2026-06-29) is a per-repo `exeris-tooling` decision driven by [RFC-2026-06-28](../exeris-tooling/docs/rfc/RFC-2026-06-28-presentation-view-emitter-tooling.md): wire the `@View` leaf field facet end-to-end — the processor populates `ComponentNodeMetadata.field` from field-level `@UI` render hints and the codegen-ts `ViewGenerator` emits the control from it — making `@View` the carrier of field-level render detail and the functional prerequisite to deprecating `@UI` (the SDK already shipped the `UIFieldMetadata`-on-leaf half; the `@View` first slice left the facet `null`). Front-only facet, so no Java emitter counterpart (Java∪TS parity by construction); carries the recurring ADR-042 `-io` reader-mirror obligation for the leaf `UIFieldMetadata`. Accepted 2026-06-29 with the founder's decisions baked in (unify on `@View`; the leaf facet is `ViewFieldMetadata`, the renamed/expanded successor of `UIFieldMetadata`; entity-driven expansion is the model; no dual-path; `@UI` removed); content in `exeris-tooling/docs/adr/ADR-047-view-leaf-field-facet-and-ui-subsumption.md`. ADR-048 (reserved 2026-06-29) holds the number for the cross-app contract mesh — generated contract registry + remote client + saga remote-dispatch (T12; capability twin T17), target 0.7.0. It is ADR-triggering and RFC-gated: codegen-core today carries only the closed-world `CapabilityGraph`, so the cross-app surface is a net-new pipeline shape designed via an RFC before content lands.
