# ADR Index — Exeris Ecosystem

**Single numbering namespace** across all Exeris repositories. ADR files live next to the code they describe; this index is the canonical lookup (number → owning repo + link).

## Rules

1. **Tech-side ADRs only.** Business decisions (legal / IP / financial / procurement) are kept in a separate, private decision registry maintained outside this repository. Refactoring-only ADRs do not enter the registry.
2. **Number reservation.** A number is reserved by a PR to this file before the ADR-content PR merges.
3. **Visibility.** Per ADR-020.
   - `public` — content lives in a public open-core repo.
   - `enterprise-private` — content lives only in a private enterprise repo. Number is publicly registered here, content is not.
4. **Scope.**
   - `per-repo` — bounded to one repo.
   - `cross-repo` — affects multiple repos. Owning repo holds the authoritative copy; every other affected repo has a `docs/adr/ADR-NNN.link.md` stub.
   - `platform` — stack-level recommendation. Owning repo: `exeris-docs`.
5. **Routines and reviewers cite by number**, not by path.

> **Reservation note:** ADR-031 is a number reservation against future name collisions; content lands in a follow-up PR. Per Rule 2, the number is held by this index entry, not by the existence of a content file. ADR-031 covers the kernel-gated half of Phase 3B (W3C `traceparent` propagation + OTel span/metric emission) and waits on a **future** kernel tracing milestone — **not** delivered in `exeris-kernel` 0.8.0. As of 0.8.0 (shipped 2026-06-03) the kernel has **no** tracing logic at all: no `TraceContext` `ScopedValue` carrier, no `PrometheusOtlpTelemetrySink`, no span emission in SPI/Core/Community (the `telemetry.tracingEnabled` / `region` config knobs are parsed but dormant). The kernel-side work is the still-open gap in the kernel ROADMAP §"Telemetry: OTLP Metrics Export and Distributed Tracing", targeted ~Sprint 0.12 / v0.12 of the consolidated 1.0 GA roadmap. ADR-031 therefore remains blocked on that milestone, not on 0.8.0; the earlier "0.8.0" pin was a drift in this note (corrected 2026-06-08). ADR-030 was previously listed as reserved; it was promoted to ACCEPTED 2026-05-17 in the same downstream review that closed Phase 4C — see the linked file. ADR-033 was similarly listed as reserved earlier on 2026-05-18 pending the RFC; it was promoted to ACCEPTED the same day after the RFC was accepted — see `exeris-kernel/docs/rfc/RFC-2026-05-18-kernel-diagnostics-spi.md`. ADR-034 covers the symmetric client-side body codec SPI (parallel to `HttpResponseBodyEncoder` from ADR-009/0.5.0) plus the tier-neutral `KernelWebClient` facade in `exeris-kernel-core`. ADR-034 supersedes ADR-026 (the original `CommunityWebClient` placement) because that decision leaked the Community tier into the build-time surface consumed by `exeris-tooling/KernelClientGenerator`; the supersession lands in lockstep across `exeris-kernel` (SPI + facade), `exeris-tooling` (generator FQN update), and `exeris-kernel-enterprise` (link stub). Pre-1.0 has no external SPI consumers, so the supersession is in-scope for v0.8 Sprint 6. ADR-036 (reserved 2026-06-03) closes the fourth codec quadrant left open after ADR-034: server-side request-body **decode** (`HttpRequestBodyDecoder` + registry + `HttpRequestDecodingContext`), mirroring the client-side `HttpResponseBodyDecoder`. Its motivation is not symmetry-for-symmetry but removal of a build-time Wall breach — today `exeris-tooling/KernelHandlerGenerator` emits a hard-wired Jackson `MAPPER` + `JacksonException` catch into every generated controller's `parseBody`, the only codec quadrant with no SPI seam. Lands lockstep across `exeris-kernel` (SPI + `CommunityJsonRequestBodyDecoder` driver + TCK), `exeris-tooling` (generator resolves the registry instead of inlining), and `exeris-kernel-enterprise` (link stub); in-scope for v0.8 Sprint 7. ADR-038 (accepted 2026-06-05) is the **SDK-side realization** of the ecosystem capability-composition model fixed in ADR-024: it records where the `@CapabilityModule`/`@Provides`/`@Requires`/`@CapabilityLifecycle` annotations are defined (`exeris-sdk-annotations`, new `capability` subpackage), that services are referenced by `Class<?>` and persisted in the AST as source-written name strings (tooling-normalized to FQN), and that the lifecycle interface, licensing taxonomy (ADR-023), and `cap-manifest.json` discovery format stay out of the SDK. It is to ADR-024 what ADR-037 is to the `-io` module: a thin "implements" record owned by `exeris-sdk`, driven by [RFC-2026-06-03](../exeris-sdk/docs/rfc/RFC-2026-06-03-capability-annotation-surface.md). ADR-041 (accepted 2026-06-09) is owned by `exeris-spring-runtime` and follows the single-decider accepted-on-merge pattern: it records the decision to re-activate Spring Boot's servlet-web-gated OAuth2 resource-server `JwtDecoder` inside Compatibility Mode when the app runs Exeris-hosted with `spring.main.web-application-type=none`, so a brownfield JWT resource server keeps working after migrating onto the Exeris runtime. It is **narrow by design** — it covers only the resource-server JWT decoder (built with public Spring Security factories, mirroring Spring Boot's own validator wiring) and explicitly defers the broader "which servlet-web-gated auto-configs does Exeris compat re-activate under `none`" policy to a future RFC. Content and the thin decoder implementation land together in the `exeris-spring-runtime` PR that introduces `docs/adr/ADR-041-compat-resource-server-security-under-none.md`.
