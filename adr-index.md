# ADR Index — Exeris Ecosystem

**Single numbering namespace** across all Exeris repositories. ADR files live next to the code they describe; this index is the canonical lookup (number → owning repo + link).

## Rules

1. **Tech-side ADRs only.** Business decisions (legal / IP / financial / procurement) are kept in a separate, private decision registry maintained outside this repository. Refactoring-only ADRs do not enter the registry.
2. **Number reservation.** A number is reserved by a PR to this file before the ADR-content PR merges.
3. **Visibility.** Per ADR-020.
   - `public` — content lives in a public open-core repo.
   - `enterprise-private` — content lives only in a private enterprise repo. Number is publicly registered here, content is not.
4. **Scope.**
   - `per-repo` — bounded to one repo.
   - `cross-repo` — affects multiple repos. Owning repo holds the authoritative copy; every other affected repo has a `docs/adr/ADR-NNN.link.md` stub.
   - `platform` — stack-level recommendation. Owning repo: `exeris-docs`.
5. **Routines and reviewers cite by number**, not by path.

Recorded because it generalises: a reservation fixes a *number*, not a slice boundary, and re-cutting the slices at finalization is the registry working rather than drifting. ADR-055 (accepted 2026-07-30) closes the last unimplemented predicate of ADR-024's four-predicate validator: predicate 4, the cap-tier Wall. It is ADR-triggering on two counts. First, **input shape** — the tooling pipeline has until now consumed exactly one input, the processor-emitted `DomainMetadata`/`capability_*.json` corpus (a hard constraint of ADR-015); a Wall guard must read the *compiled* cap classes, which is a second input class and therefore a pipeline-shape change, not a refactor. Second, **enforcement locus** — ADR-024 obligation 3 placed the Wall in per-repo ArchUnit-style guards and conceded that "modifying or disabling the guards is a registry violation reported through periodic audits", i.e. a social control; moving the check into the pipeline that already runs `@Requires` resolution (which the ADR-024 body itself anticipates at §"The Wall, extended to capabilities") makes it mechanical and non-disableable, and obligation 3's per-repo guards become defence-in-depth rather than the primary gate. Two implementation findings are load-bearing enough to record with the decision: (a) **bytecode, not sources** — founder-ruled 2026-07-29, because a source scan sees only the cap's own files and is blind to a forbidden type that arrives transitively when a dependency changes; (b) the scan needs **no new dependency and specifically not ASM** — `exeris-tooling` enforces JDK exactly `[26,27)`, so the JDK-standard Class-File API (JEP 484, final in JDK 24) suffices, and a constant-pool `ClassEntry` walk alone is *unsound* (it misses types appearing only in field/method descriptors or generic `Signature` attributes, so a `void configure(ApplicationContext)` cap method would pass), making the extraction surface — pool ∪ descriptors ∪ signatures ∪ annotations — the load-bearing part of the design rather than the forbidden-prefix list. Note also that the ADR-024 body's clause "an SKU manifest that contains a cap with disabled or stale Wall guards is rejected by the kernel at boot" is **stale** post the 2026-06-17 "Validation Stamp Lifecycle" amendment, which made the kernel cap-blind; ADR-055 records the correct locus (build-time tooling gate, boot-time stamp assertion in the platform composition runtime) without reopening that amendment. ADR-058 (accepted 2026-07-31) is ADR-triggering on the same **pipeline-shape** ground as ADR-055, one layer out: until now every emitted artefact landed in a single output tree owned by one `OutputWriter` and one T13 manifest, and a generated *test* cannot — emitted under `src/main/generated` it would compile into the application artefact and put JUnit on its runtime classpath. The second root is therefore a shape change, not a new generator. Its second half is a contract this repo cannot enforce and must therefore state: tooling emits no `pom.xml`, so whatever a generated test imports becomes a hard requirement on every downstream project that sets `-Dexeris.tests=true`. The ruling fixes that at JUnit 5 + AssertJ and emits the doubles instead of mocking (an `HttpExchange` recorder overriding even the interface's default `respond(...)` overloads, which would otherwise need a runtime-bound encoder; a service stub that subclasses the generated service). That makes three properties of generated code load-bearing rather than incidental — `public`, non-final, assignment-only constructors — and the e2e gate enforces them by **running** the emitted tests through the JUnit Platform launcher rather than merely compiling them, since a test emitter whose output is never executed is exactly the inert-output failure mode the repo rejects elsewhere. The FE half of T2 is deliberately a separate slice: the emitted Angular app declares `"test": "ng test"` but ships no runner and no test dependencies, so emitting specs without wiring `@angular/build:unit-test` (Vitest, founder-ruled the same day) would produce specs nobody can run. ADR-072 (reserved 2026-08-18, `exeris-sdk`) is the registry's first **number collision caught after drafting rather than before**, and is recorded here because the failure mode is structural rather than careless. It was written as `ADR-070` against a local checkout of this index that ended at `068`; upstream, `070` was already `exeris-tooling`'s generated composition root and `071` the kernel's operational-limits path, so the content renumbered to `072` before either row could conflict. Note which rule this does and does not breach: **Rule 2 above is satisfied** — it requires the number to be reserved before the *content PR merges*, and this row lands ahead of exeris-sdk#100. What was inverted is the stricter ecosystem rule in `~/exeris-systems/CLAUDE.md` ("reserve the number in the index **first**, then write the content"), which exists precisely to prevent drafting against a number someone else holds. The reason the inversion went unnoticed is that a stale local index gives **no signal at all** — one number namespace spans ~20 repos, so two authors can draft against the same number and nothing fails until their ADRs meet. The operational addition: fetch this repo before taking a number, not after. Rule 2 was in fact met here by **67 seconds** — the reservation row landed 2026-08-18T13:37:47Z and `exeris-sdk`#100 merged at 13:39:54Z — which is the rule satisfied, not a process. **A second lesson, from finalizing this same number:** promotion is *two* edits in the main table, the status cell and the Link cell, and the commit title is not one of them. `docs(adr-index): finalize ADR-072 on merge — accepted, linked, cross-repo` (#64) rewrote the summary cell and added the cross-repo stubs row while leaving status at `reserved (… row to be finalized on merge)` and Link at `_(content in flight …)_`, so the registry disagreed with itself three lines apart until #68. #66 had to fix the same shape for ADR-066 and ADR-071 in the same week ("both shipped, both still read reserved"). A finalize PR that does not touch the status cell has not finalized anything.
